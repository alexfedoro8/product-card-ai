# AI-помощник для карточек товаров КИП

Прототип сервиса, который по данным о контрольно-измерительном приборе готовит **черновик карточки товара для B2B-магазина**:

- SEO-заголовок до 70 символов;
- SEO-описание на 800–1200 символов;
- структурированную таблицу характеристик;
- 3–5 поисковых запросов;
- коммерческий блок для менеджера: кому подходит прибор и какие задачи решает.

Главное требование: **сервис не выдумывает характеристики**. Технические значения берутся только из входных данных, это проверяет код, а не только промпт. Всё, чего нет, помечается «данных нет» и попадает в список «Требует уточнения у поставщика».

## Быстрый старт

Нужен [uv](https://docs.astral.sh/uv/). Python нужной версии uv скачает сам.

```bash
# 1. Установить зависимости
uv sync

# 2. Указать ключ модели
cp .env.example .env          # Windows: copy .env.example .env
#    откройте .env и впишите ключ одного провайдера, например OPENROUTER_API_KEY=sk-or-...

# 3. Запустить
uv run uvicorn app.main:app --reload
```

После запуска доступны:
- панель для контент-менеджера: http://127.0.0.1:8000
- Swagger: http://127.0.0.1:8000/docs
- проверка настройки: http://127.0.0.1:8000/health (показывает провайдера и модель, сам ключ не выводит)

## Провайдеры LLM

Провайдер выбирается **автоматически по ключу**, который задан в `.env`. Если ключей несколько, порядок приоритета совпадает с таблицей. Выбрать провайдера явно можно через `LLM_PROVIDER`.

| Провайдер | Переменная | Модель по умолчанию | API |
|---|---|---|---|
| OpenRouter | `OPENROUTER_API_KEY` | `openai/gpt-4o-mini` | OpenAI-совместимый |
| OpenAI | `OPENAI_API_KEY` | `gpt-4o-mini` | OpenAI |
| DeepSeek | `DEEPSEEK_API_KEY` | `deepseek-chat` | OpenAI-совместимый |
| Anthropic Claude | `ANTHROPIC_API_KEY` | `claude-haiku-5-5` | нативный Messages API |

Модель меняется через `LLM_MODEL`. Через `LLM_BASE_URL` можно подключить любой OpenAI-совместимый сервер, в том числе локальную модель. Ключ в репозиторий не попадает: `.env` добавлен в `.gitignore`.

## Как пользоваться

**Панель** (http://127.0.0.1:8000). Слева форма: название, производитель, категория, характеристики строками «название — значение», описание, ссылки на фото. Есть вкладка JSON для ввода готового объекта. Справа черновик карточки в виде страницы магазина, плюс вкладки Markdown и JSON. Первым идёт блок **«Оценка введённых данных»**: проверка результата по каждому требованию задания (заголовок, длина описания, характеристики, запросы, коммерческий блок, фото, отсутствие выдуманных значений). У невыполненных пунктов сказано, что дать на вход, ниже — список «Как улучшить карточку». При бедных данных часть требований честно не выполняется: сервис не добирает объём домыслами, а говорит, какой информации не хватает (характеристики, текст паспорта, фото). Та же оценка есть в API-ответе (поле `data_quality`).

Фото можно добавить **файлом** (кнопка «Загрузить фото», JPEG/PNG/WebP/GIF до 10 МБ) или ссылкой. Файлы сохраняются локально в `uploads/` (папка в `.gitignore`); тип проверяется по сигнатуре файла, а не по расширению.

Кнопки: «Копировать» у каждого блока, «Скачать .md / .json», «Печать / PDF».

**API / Swagger.** `POST /api/v1/cards`; в Swagger подставлена структура запроса из задания.

```bash
curl -X POST http://127.0.0.1:8000/api/v1/cards \
  -H "Content-Type: application/json" \
  -d @product.json
```

Загрузка фото через API: `POST /api/v1/images`, тело — сам файл; в ответе ссылка для поля `images`.

```bash
curl -X POST http://127.0.0.1:8000/api/v1/images --data-binary @photo.jpg -H "Content-Type: image/jpeg"
```

**Командная строка.** Пакетный прогон по JSON-файлам товаров пишет `.json` и `.md` в `examples/output/`:

```bash
uv run python -m app.cli товар1.json товар2.json
```

Формат входных данных:

```json
{
  "name": "Манометр показывающий DM 02",
  "manufacturer": "Манотомь",
  "category": "Манометры технические",
  "specs": {"диапазон измерений": "0–1,6 МПа", "класс точности": "1,5"},
  "description": "Прибор предназначен для измерения избыточного давления...",
  "images": ["https://.../photo.jpg"]
}
```
Обязательно только поле `name` и хотя бы одно из полей `specs` или `description`.

## Пример результата

Результаты генерации лежат в [`examples/output/`](examples/output/): Markdown для вставки в CMS и полный JSON-ответ API. Их можно получить в панели кнопками «Скачать .md» и «Скачать .json» или пакетно через CLI.

## Как устроено

```
Панель / Swagger / CLI
  → ProductInput (Pydantic)        валидация: битый JSON, пустое имя, нет данных → 422
  → normalize                      чистка specs; «», «—», «н/д» → список пустых полей
  → checklist                      тип прибора по названию → обязательные поля → чего не хватает
  → LLM                            промпт + данные товара + список отсутствующих полей
  → LLMDraft (Pydantic)            ответ модели — строго JSON
  → validators                     длины; каждое число в тексте есть во входе;
                                   нет «нержавейки», HART, Ex, гарантии и т. п. из воздуха;
                                   цитаты из описания дословные
  → нарушения? → повтор с конкретной обратной связью (до 3 попыток),
                 иначе лучший вариант + замечания для человека
  → CardResponse                   таблицу характеристик собирает код; missing_fields; markdown
```

### Ключевые решения

1. **Таблицу характеристик собирает код, а не модель.** Модель пишет только тексты. Характеристики в таблице — это входные `specs` один в один.
2. **Значения из текстового описания подтверждаются цитатой и не теряются.** Модель может найти в описании параметр, которого нет в `specs` (например, «IP40»), но обязана приложить дословную цитату. Код ищет цитату в описании и сверяет числа. Без подтверждения значение отбрасывается. В карточке такие значения помечены «из описания», цитата видна при наведении. Если в описании есть значения (например, «У2 и Т2», «5–25 Гц», «3 года»), которые не попали ни в `specs`, ни в извлечённые характеристики, модель получает повтор: «вынеси их в таблицу с цитатой».
3. **Проверка «выдуманных» чисел.** Код находит все числа в сгенерированных текстах (с учётом «1,6» = «1.6») и сверяет их со входом. То же делается для типичных выдумок про КИП: материал, взрывозащита, протоколы связи, поверка, гарантия, цены и доставка.
4. **Текст строится строго из введённого, объём — по количеству фактов.** Норма 800–1200 символов конфликтует с бедными входными данными, и модель начинает добирать объём выдуманными сценариями применения, монтажа и «пользой для покупателя». Поэтому:
   - промпт запрещает всё, чего нет во входе: сценарии и объекты применения, отрасли, монтаж, эксплуатацию, выводы о пользе, оценки. Тип изделия передаётся модели только как служебная подсказка, а не как источник свойств;
   - код ловит это по словарям (трубопроводы, котельные, энергетика, «отличный», «удобно», «позволяет»…) и отправляет на переделку, если такого слова нет во входных данных;
   - короткое описание **не переделывается**, а сопровождается замечанием «во входных данных недостаточно фактов — дополните описание или паспорт». Мало данных — сухая короткая карточка. Порогов по типам изделий нет: в форму может прийти любое изделие, и правило «только факты» универсально;
   - слишком длинное описание и заголовок длиннее 70 символов уходят на переделку с конкретной цифрой.
5. **Подсказка «чего не хватает» для распознанных типов КИП** (манометр, датчик давления, термометр, расходомер), включая номер в Госреестре СИ и межповерочный интервал. Это рекомендация для запроса поставщику, она не влияет на текст. Если тип не распознан, обязательные поля не придумываются: в «Требует уточнения» попадают только реальные пробелы (пустые поля, нет производителя, описания, фото).
6. **Фото не генерируется.** Принимаются ссылки от производителя. Если ссылок нет, появляется пункт «Фото товара — запросить у производителя». Сгенерированное изображение прибора — та же выдуманная характеристика, только визуальная.

### Промпты

Промпты лежат в [`prompts/`](prompts/), а не в коде.
- [`system.md`](prompts/system.md) — роль (технический копирайтер B2B-магазина КИП), жёсткие правила «только входные данные», требования к каждому полю, самопроверка перед ответом. Описание оформляется как в карточках производителей: вводный абзац о назначении, затем «Основные характеристики:» списком «- Название — значение», каждый параметр с новой строки. Код проверяет, что параметры оформлены списком, и приводит маркеры («•», «–») к единому виду.
- [`user.md`](prompts/user.md) — данные товара в JSON, определённый тип прибора и **явный список отсутствующих полей**, чтобы модель не пыталась их заполнить.
- [`retry.md`](prompts/retry.md) — обратная связь от валидаторов при повторе.

Температура 0,3: нужна стабильность, а не креатив. Ответ запрашивается в JSON-режиме. Если модель его не поддерживает, клиент повторяет запрос без него, а парсер извлекает JSON из ответа.

## Обработка ошибок

| Ситуация | Ответ |
|---|---|
| Некорректный JSON | 422, «Некорректный JSON (позиция N): …» |
| Пустое название, неверный тип поля, битая ссылка на фото | 422, сообщение с именем поля |
| Нет ни характеристик, ни описания | 422, «недостаточно данных для карточки» |
| Пустые отдельные поля | карточка создаётся, поле в «Требует уточнения» |
| Не задан ключ или неверный `LLM_PROVIDER` | 503 с подсказкой, что указать в `.env` |
| Неверный ключ, модель не найдена, нет средств | 502 с понятной причиной |
| Таймаут, 429, 5xx | автоматические повторы с паузой (SDK), затем 504 / 502 |
| Модель вернула не JSON или нарушила правила | повтор с обратной связью, затем результат с замечаниями |

## Архитектура

```
app/
  main.py                 фабрика приложения create_app(): роутеры, статика, обработчики ошибок
  cli.py                  пакетный прогон из командной строки
  core/                   общее ядро
    config.py             Settings, реестр провайдеров LLM, пути
    errors.py             AppError → ConfigError, LLMError, ImageError (код + HTTP-статус)
    rules.py              CardRules: требования к карточке (70 / 800–1200 / 3–5…)
    normalize.py          очистка входных данных
  api/                    HTTP-слой, без бизнес-логики
    dependencies.py       сборка зависимостей через FastAPI Depends
    errors.py             единый формат ошибок, сообщения валидации по-русски
    routes/               cards, images, system, pages
  schemas/                Pydantic-схемы: product, llm (ответ модели), card (результат), errors
  llm/                    клиенты моделей
    base.py               протокол LLMClient
    openai_client.py      OpenRouter, OpenAI, DeepSeek
    anthropic_client.py   Claude
    factory.py            реестр «вид API → клиент», create_client, LazyLLMClient
  validation/             проверки ответа модели
    base.py               протокол DraftCheck, CheckContext
    checks.py             LengthCheck, ListFormatCheck, GroundedNumbersCheck, TermsCheck, ExtractionCoverageCheck
    terms.py              словари выдумок
    validator.py          DraftValidator — прогоняет набор проверок
    extraction.py         проверка цитат из описания
  services/               бизнес-логика
    card_generator.py     CardGenerator — фасад генерации
    prompts.py            PromptBuilder (шаблоны из prompts/)
    parsing.py            разбор ответа модели
    specs.py              таблица характеристик и «требует уточнения»
    checklist.py          подсказки полей для распознанных типов КИП
    quality.py            QualityAssessor — оценка введённых данных
    rendering.py          CardRenderer / MarkdownRenderer
    storage.py            ImageStorage / LocalImageStorage
  templates/, static/     панель ввода и вывода
prompts/                  промпты
examples/output/          результаты генерации
tests/                    pytest
```

**Принципы:**
- **Одна ответственность.** Маршруты только принимают HTTP-запрос и отдают ответ; генерация, проверки, оценка данных, рендер и хранение фото — отдельные классы.
- **Открытость к расширению.** Новая проверка ответа модели — класс с методом `check()` и строка в `default_checks()`. Новый провайдер — запись в `PROVIDERS`, новый вид API — `register_client()`. Новый формат выдачи — класс с методом `render()`, новое хранилище фото — класс с методом `save()`, другие требования к карточке — свой `CardRules`. `CardGenerator` при этом не меняется: тесты показывают подключение своей проверки и своего клиента.
- **Зависимость от абстракций.** `CardGenerator` получает клиента модели, валидатор, оценщика и рендерер через конструктор и работает с протоколами (`LLMClient`, `DraftCheck`, `CardRenderer`, `ImageStorage`). В API всё собирается в `api/dependencies.py`, в тестах подменяется через `dependency_overrides`.
- **Паттерны:** Strategy (проверки, клиенты LLM), Factory + Registry (`create_client`), Facade (`CardGenerator`), Proxy (`LazyLLMClient`: ошибки ввода 422 проверяются раньше, чем наличие ключа 503), Dependency Injection, App Factory (`create_app`).

## Ограничения и что можно улучшить

**Ограничения текущей версии**
- Код проверяет числа, типичные выдумки, оценочные слова и отрасли по словарям, но не смысл фраз. Утверждение без цифр и без слов из словарей может пройти. Поэтому карточка — черновик для проверки человеком.
- При бедных входных данных описание может оказаться короче 800 символов: это сделано сознательно (см. «Борьба с „водой“»), карточка помечается замечанием.
- Тип прибора определяется по ключевым словам в названии. Подсказки «чего не хватает» есть для четырёх типов КИП; для остальных изделий сервис сообщает только о реальных пробелах во введённых данных.
- Сервис гарантирует верность **введённым** данным, а не реальности. Если во входе ошибка (например, в поле «Производитель» указан город склада или класс точности исполнения «по заказу» вместо базового), она попадёт в карточку. Сверка с паспортом — задача человека.
- Одна характеристика — одно значение: варианты «базовое / по заказу» (IP40 или IP54) передаются одной строкой.
- Названия характеристик не приводятся к справочнику: «Диапазон», «Пределы измерений» и «Шкала» остаются как во входе.
- Один товар за запрос через API; пакетная обработка только в CLI.
- Нет кеша: повторный запрос с теми же данными снова идёт в модель.

**Что можно улучшить**
- **Локальная модель вместо облачного API** — DeepSeek, Qwen или Llama через [Ollama](https://ollama.com) (или vLLM / LM Studio). Данные о товарах и ассортименте не покидают контур компании, нет оплаты за токены, сервис работает без интернета. Архитектура к этому готова: Ollama отдаёт OpenAI-совместимый API, поэтому подключение уже сейчас делается настройками, без правок кода:
  ```env
  LLM_PROVIDER=openai
  OPENAI_API_KEY=ollama                      # Ollama ключ не проверяет, но поле должно быть заполнено
  LLM_BASE_URL=http://localhost:11434/v1
  LLM_MODEL=qwen2.5:7b                       # или deepseek-r1:8b, llama3.1:8b
  ```
  Что стоит доработать для полноценной поддержки:
  - отдельный провайдер `ollama` в реестре `PROVIDERS`, которому не нужен ключ;
  - вырезать из ответа блок рассуждений `<think>…</think>`, который выдают модели семейства DeepSeek-R1, до разбора JSON;
  - сравнить модели на наборе эталонных карточек (см. следующий пункт). Небольшие локальные модели хуже держат длинные инструкции на русском, поэтому повторов будет больше. Защита от выдуманных значений при этом не ослабевает: числа, технические утверждения и сценарии применения сверяет с входными данными код, а не модель.
- Набор эталонных карточек и автоматические evals: доля выдуманных фактов, попадание в длины, качество запросов. Плюс LLM-as-judge для проверки соответствия текста фактам.
- Справочник характеристик и единиц измерения по категориям каталога с нормализацией названий.
- Structured Outputs (JSON Schema) у провайдеров, которые его поддерживают.
- Пакетная загрузка из CSV/XLSX или выгрузки 1С и экспорт в формат CMS магазина.
- Кеш по хешу входных данных, учёт стоимости токенов, история версий карточки.
- Сбор SEO-запросов по реальной частотности (Wordstat) вместо генерации моделью.
- Загрузка скана или PDF паспорта с извлечением текста (OCR / мультимодальная модель) прямо в поле «Описание».
- Хранение загруженных фото в объектном хранилище вместо локальной папки.
